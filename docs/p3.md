# Worked example: parsing P3 (the AOL client protocol)

P3 is the link protocol the America Online client used to talk to AOL's host
computers, from the dial-up days through AOL 9. OSCAR (see
[oscar.md](oscar.md)) came later and was used by AIM and ICQ. P3 is a small
reliable-delivery protocol: framed, numbered, CRC-checked packets. Its
DATA packets carry a two-character *token* naming the message, followed by
an *FDO91* atom stream (FDO is AOL's form and display language).

```
byte stream ─▶ P3 packets (sync, CRC, length, sequence numbers, type) ─▶ token + FDO atoms
```

[`examples/p3.packet`](../examples/p3.packet) describes the formats. Every
packet below has test vectors in [`tests/specs/p3.json`](../tests/specs/p3.json),
checked in all six languages. The demos
([`examples/p3_demo.py`](../examples/p3_demo.py),
[`examples/p3_demo.rs`](../examples/p3_demo.rs)) run in the test suite.

## Sources and confidence

AOL never published P3. The layout here follows
[notaol](https://github.com/chfoo/notaol), an open-source P3 client by an
Archive Team member, and the
[Archive Team AOL page](https://wiki.archiveteam.org/index.php/AOL), and
was then checked against a real AOL 4.0 client (Windows 95 in DOSBox-X)
signed on to [aolserver](https://github.com/kachowtowmater/aolserver), an
open-source AOL host whose `re/NOTES.md` documents the client's AOLP3 tool.
The [p3-conformance](../../p3-conformance) harness replays such sessions:

* **Confirmed against captures:** the 8-byte header, the CRC (CRC-16/ARC
  over bytes 3 up to the stop byte), the `**` that AOL 4.0 over TCP sends
  in its place, the length rule (data + 3), the high bit of the type byte
  (set by the client, clear in the host's packets), and the INIT packet.
  notaol's test suite contains a real INIT packet, which is the first test
  vector here; its CRC `0xb35f` is reproduced independently. Packets from
  an AOL 4.0 session (INIT, ACKs, `K1` and `aT` DATA) are vectors too.
  FDO's two-byte argument length (`varint15`) is checked the same way:
  with it, every `aT` stream the host sent in that session (and in
  p3-conformance's scripted runs against aolserver) parses as uncompressed
  atoms.
* **From notaol and the AOLP3 notes (not a capture):** the packet type numbers,
  the 0x10-0x7F sequence range, the token + atom-stream layout of DATA
  packets, and the uncompressed FDO atom encoding. The `Dd` login vector is
  built exactly the way notaol builds its login packet.
* **Uncertain:** notaol's names for most INIT fields. Only the platform,
  client version, `session_flags`, `num_colors` and `speed` are checked by
  its tests. In the capture, `horizontal_res`/`vertical_res` do not contain
  a screen resolution, so treat those names as placeholders.

## 1. Framing

```
const P3_SYNC uint8 = 0x5a "first byte of every packet ('Z')"
const P3_STOP uint8 = 0x0d "last byte of every packet (carriage return)"
const P3_LENGTH_OVERHEAD uint16 = 3 "`length` counts tx_seq, rx_seq and the type byte as well as the data"
const P3_SEQ_FIRST uint8 = 0x10 "sequence numbers run from P3_SEQ_FIRST to P3_SEQ_LAST, then wrap"
const P3_SEQ_LAST uint8 = 0x7f
const P3_NO_CRC uint16 = 0x2a2a "\"**\": AOL 4.0 over TCP sends this instead of a CRC once INIT is acknowledged"

// P3 packet types (the `type` member). Control packets carry no data, or
// a byte or two (RAK: 1 = re-init, 2 = connected). SS and SSR come from
// notaol; RESET, RAK, SETUP and ACKNOW from the AOL client's AOLP3 tool.
const P3Type u7 {
  data = 0x20       "numbered message carrying a token and FDO atoms",
  ss = 0x21         "ask the peer for a status report (SSR)",
  ssr = 0x22        "status report: lists messages to retransmit",
  init = 0x23       "first packet sent by the client",
  ack = 0x24        "acknowledge / null message",
  nak = 0x25        "a damaged or out-of-order packet was received",
  heartbeat = 0x26  "keep-alive; answer with an ACK",
  reset = 0x28      "reset (the client ignores it)",
  rak = 0x29        "reset acknowledge: data byte 1 = send INIT again, 2 = connected",
  setup = 0x2a      "setup",
  acknow = 0x2b     "acknowledge now",
}

// Every packet, whatever its type: the type picks how the body is read.
packet P3Packet be {
  sync uint8 == P3_SYNC,
  // CRC-16/ARC of everything from `length` up to the stop byte, or "**"
  // (AOL 4.0 over TCP, after INIT): decoders accept both, encoders write
  // "**" when `crc` holds it and the real CRC otherwise.
  crc uint16 = crc16_arc(length..body) placeholder P3_NO_CRC,
  length uint16 = sizeof(tx_seq..body),  // the body + P3_LENGTH_OVERHEAD
  tx_seq uint8,             // P3_SEQ_FIRST..P3_SEQ_LAST
  rx_seq uint8,             // last sequence number received from the other side
  kind bitfield uint8 {
    from_client u1,         // set on the client's packets, clear on the host's
    type u7 : P3Type strict
  },
  body switch type {
    P3Type.data => data P3Message,
    P3Type.init => init P3Init,
    _ => control bytes[]    // the control packets: usually empty
  } size length - P3_LENGTH_OVERHEAD,
  stop uint8 == P3_STOP
}
```

* The magic numbers are **named constants**. `P3Type` is a category of
  `u7` values, and `type u7 : P3Type` notes where `type`'s values come
  from. Every generated file exports them (`P3Type.INIT` in Python,
  `P3Type::INIT` in Rust, `P3TypeInit` in Go, `P3TYPE_INIT` in C), so the
  demos never spell out `0x23`.
* The **type byte is a bitfield**. The top bit says which side sent the
  packet: the client sets it (`0xA3` on the wire is its INIT, 0x23), the
  host leaves it clear (`0x24`, an ACK). The packet type is the low 7 bits;
  encoding checks that `type` fits in 7 bits.
* `body switch type { ... }` is a **tagged union**: the packet type picks how
  the body is decoded (a `P3Message` for DATA, a `P3Init` for INIT, raw
  bytes otherwise), so one description covers every packet type.
* `size length - P3_LENGTH_OVERHEAD` gives the body a **window** of exactly
  that many bytes. The body cannot read past it, and a body shorter than
  its window (an INIT a newer client extended) still decodes. A length past
  the end of the input, or below 3, is an error.
* The framing bytes are **checked**: `sync uint8 == P3_SYNC`, `stop uint8
  == P3_STOP` and `type u7 : P3Type strict`. A packet
  that breaks one of them is a `constraint` error naming the field
  (`P3Packet.stop`) in every language. Members declared `== value` also
  start out holding that value, so building a packet only needs the
  interesting fields.

`packet_builder layout examples/p3.packet` lists every constant with its
note after the packet layouts.

## 2. Lengths and the CRC

`length` and `crc` are **derived fields**: the description says how to
compute them, and the generated code does the rest.

```
crc uint16 = crc16_arc(length..body) placeholder P3_NO_CRC,
length uint16 = sizeof(tx_seq..body),
```

* Decoding checks both. A packet whose CRC does not match the bytes from
  `length` through the body is a `mismatch` error naming `P3Packet.crc`, so
  the captured packets above are verified as they are decoded.
* AOL 4.0 over TCP stops computing CRCs once INIT is acknowledged and sends
  `**` (`P3_NO_CRC`) instead, both ways. `placeholder P3_NO_CRC` says so:
  decoders accept the CRC or `**` (anything else is still a mismatch), and
  encoders write `**` when `crc` holds it, so a captured packet re-encodes
  byte for byte.
* Otherwise encoding ignores whatever `length` and `crc` hold. It writes
  placeholders, then patches them once the bytes they measure are written:
  `length` first, since the CRC covers it. Building a control packet is one
  line (add `crc=P3_NO_CRC` for the TCP form):

```python
P3Packet(tx_seq=tx_seq, rx_seq=rx_seq, type=P3Type.ACK, body=P3PacketBody("control", b"")).encode()
```

`crc16_arc` is one of the built-in algorithms (CRC-8/16/32 variants, the
Internet checksum, Fletcher-16, sum8, xor8). `sizeof(a..b)` and
`offsetof(f)` measure the encoded bytes the same way.

## 3. DATA: tokens and FDO atom streams

```
const P3_TOKEN_LENGTH uint16 = 2 "every DATA packet starts with a two-character token"

packet P3Message be {
  token char[P3_TOKEN_LENGTH],  // e.g. "Dd" (login), "SD" (go ahead after INIT)
  atoms bytes[]
}

const FdoStyle u3 {
  full = 0  "uncompressed: protocol, atom number, argument length, argument",
}

const FdoProtocol u5 {
  uni = 0  "universal atoms (streams, data handling)",
  man = 1  "form manager",
  de = 3   "display editor",
}

packet FdoAtom be {
  head bitfield uint8 {
    style u3 : FdoStyle,
    protocol u5 : FdoProtocol
  },
  atom uint8,
  arg_length varint15 = len(arg),  // 1 byte below 0x80, else 2 with the top bit set
  arg bytes[arg_length],
  calc uncompressed uint8 = style == FdoStyle.full
}

packet FdoStream be {
  stream_id uint16,
  atoms FdoAtom[]
}
```

* The token is a `char[2]` **string**: you compare it with `"Dd"`, not with
  bytes.
* FDO atoms start with another bitfield: a 3-bit compression style and a
  5-bit value. Clients send the uncompressed style 0, which this
  description models exactly, and so did every host stream checked so far.
  FDO also defines compressed styles 1-7, whose layouts differ; a union on `style` could describe them, but their exact
  layouts are not well documented, so they are not modelled. `uncompressed`
  tells you when to stop.
* An argument length under 0x80 takes one byte; longer arguments (the
  host's alerts and Welcome screens, IMs over 127 characters) take two,
  `0x80 | n >> 8` then `n & 0xff`. That is the `varint15` type, so
  `arg_length` stays derived from the argument and encoders pick the form.

The `Dd` login stream is a sequence of `uni`, `man` (context) and `de`
(data entry) atoms. The screen name and password are the arguments of the
two `de_data` atoms (`FdoProtocol.de`, atom 1).

## 4. Decoding a session (Python)

```
$ cargo run -- generate examples/p3.packet -l python -p packets -o examples/out
$ PYTHONPATH=examples/out python3 examples/p3_demo.py
INIT from a Windows client, version 157.17, session flags 0x14d1
DATA token 'Dd', 83 byte(s) of FDO atoms
login: screen name 'someguy', password *********
ACK reply: 5afa0d00031010a40d
```

The core of the demo:

```python
for packet in packets(STREAM):               # framing and CRC are checked while decoding
    if packet.body.kind == "init":           # the type picked the arm
        init = packet.body.value
        print(init.platform, init.client_major, init.client_minor)
    elif packet.body.kind == "data":
        message = packet.body.value
        if message.token == "Dd":
            fields = [a.arg.decode() for a in FdoStream.decode(message.atoms).atoms
                      if a.uncompressed and (a.protocol, a.atom) == (FdoProtocol.DE, 1)]
```

## 5. The same in Rust

([full program](../examples/p3_demo.rs))

```rust
let mut reader = PbReader::new(&bytes);
while reader.remaining_bits() > 0 {
    let packet = P3Packet::decode_from(&mut reader)?;   // a bad CRC is an error
    if let P3PacketBody::Data(message) = &packet.body {
        let stream = FdoStream::decode(&message.atoms)?;
        println!("{}: {} atoms, crc 0x{:04x}", message.token, stream.atoms.len(), packet.crc);
    }
}
```

`type` is a Rust keyword, so the member is `r#type`. It is `type_` in C,
`Type` in Go and C#, and `@"type"` in Zig.

## 6. What's covered, and what isn't

| part | packet | tested with |
|------|--------|-------------|
| framing, all packet types | `P3Packet` | captured INIT, ACK, NAK, HEARTBEAT, DATA, malformed frames |
| DATA packets | `P3Packet` (`data` arm), `P3Message` | `Dd` login, `SD` |
| INIT | `P3Packet` (`init` arm), `P3Init` | captured INIT |
| FDO atoms | `FdoStream`, `FdoAtom` | login stream; a 200-byte argument (two-byte length); a compressed atom is flagged |

Not covered: compressed FDO atoms aren't decoded, and the 49-byte INIT
variant some clients send is left out.
