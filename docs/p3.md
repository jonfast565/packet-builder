# Worked example: parsing P3 (the AOL client protocol)

P3 is the link protocol the America Online client used to talk to AOL's host
computers, from the dial-up days through AOL 9. OSCAR (see
[oscar.md](oscar.md)) came later and was used by AIM and ICQ. P3 is a small
reliable-delivery protocol: framed, numbered, CRC-checked packets. Its
DATA packets carry a two-character *token* naming the message, followed by
an *FDO91* atom stream (FDO is AOL's form and display language).

```
byte stream ─▶ P3 packets (sync, CRC, length, sequence numbers, type) ─▶ token + FDO atoms
```

[`examples/p3.packet`](../examples/p3.packet) describes the formats. Every
packet below has test vectors in [`tests/specs/p3.json`](../tests/specs/p3.json),
checked in all six languages. The demos
([`examples/p3_demo.py`](../examples/p3_demo.py),
[`examples/p3_demo.rs`](../examples/p3_demo.rs)) run in the test suite.

## Sources and confidence

AOL never published P3. The layout here follows
[notaol](https://github.com/chfoo/notaol), an open-source P3 client by an
Archive Team member, and the
[Archive Team AOL page](https://wiki.archiveteam.org/index.php/AOL):

* **Confirmed against a capture:** the 8-byte header, the CRC (CRC-16/ARC
  over bytes 3 up to the stop byte), the length rule (data + 3), the
  high bit of the type byte, and the INIT packet. notaol's test suite
  contains a real INIT packet, which is the first test vector here. Its
  CRC `0xb35f` is reproduced independently.
* **From notaol's implementation (not a capture):** the packet type numbers,
  the 0x10-0x7F sequence range, the token + atom-stream layout of DATA
  packets, and the uncompressed FDO atom encoding. The `Dd` login vector is
  built exactly the way notaol builds its login packet.
* **Uncertain:** notaol's names for most INIT fields. Only the platform,
  client version, `session_flags`, `num_colors` and `speed` are checked by
  its tests. In the capture, `horizontal_res`/`vertical_res` do not contain
  a screen resolution, so treat those names as placeholders.

## 1. Framing

```
packet P3Packet be {
  sync uint8,               // always 0x5A ('Z')
  crc uint16,               // CRC-16/ARC of everything from `length` up to the stop byte
  length uint16,            // tx_seq + rx_seq + type + data, i.e. data bytes + 3
  tx_seq uint8,             // sequence numbers run 0x10..0x7F and wrap to 0x10
  rx_seq uint8,
  kind bitfield uint8 {
    always_set u1,          // the high bit of the type byte is always 1
    type u7                 // 0x20 DATA ... 0x26 HEARTBEAT
  },
  data bytes[length - 3],
  stop uint8,               // always 0x0D ('\r')
  calc valid uint8 = sync == 0x5a and stop == 0x0d and always_set == 1
                     and type >= 0x20 and type <= 0x26 and length >= 3
}
```

* The **type byte is a bitfield**. The top bit is always set (`0xA3` on the
  wire is INIT, 0x23), so the packet type is the low 7 bits. Encoding checks
  that `type` fits in 7 bits.
* `bytes[length - 3]` sizes the data from the header. A length below 3 is
  a negative size, and a length past the end of the input is rejected
  before anything is allocated. Both are decode errors in every language.
* `valid` collects the framing checks. A packet with a bad sync or stop
  byte still decodes, so you can log it, but `valid` is 0.

| type | name | meaning |
|------|------|---------|
| 0x20 | DATA | numbered message: token + FDO atoms |
| 0x21 | SS | ask the peer for a status report |
| 0x22 | SSR | status report: messages to retransmit |
| 0x23 | INIT | first packet from the client |
| 0x24 | ACK | acknowledge / null message |
| 0x25 | NAK | damaged or out-of-order packet received |
| 0x26 | HEARTBEAT | keep-alive; answer with ACK |

`P3DataPacket` and `P3InitPacket` describe a whole DATA or INIT packet in
one pass. Their token, atoms and INIT fields replace the generic `data`.

## 2. The CRC

packet-builder does not compute checksums (yet), so the CRC is an ordinary
`uint16` field and the application checks it. It takes a few lines, and the
reader's position gives you the raw bytes of each packet:

```python
def crc16_arc(data):
    crc = 0
    for byte in data:
        crc ^= byte
        for _ in range(8):
            crc = (crc >> 1) ^ 0xA001 if crc & 1 else crc >> 1
    return crc

reader = PbReader(stream)
while reader.remaining_bits() > 0:
    start = reader.position_bits() // 8
    packet = P3Packet.decode_from(reader)
    raw = stream[start:reader.position_bits() // 8]
    assert packet.valid and crc16_arc(raw[3:-1]) == packet.crc
```

To send a packet, encode it once, compute the CRC over the same range, set
`crc` and encode again (`control_packet` in the demo does this).

## 3. DATA: tokens and FDO atom streams

```
packet P3Message be {
  token char[2],            // e.g. "Dd" (login), "SD" (go ahead after INIT)
  atoms bytes[]
}

packet FdoAtom be {
  head bitfield uint8 {
    style u3,               // compression style; 0 = uncompressed
    protocol u5             // atom protocol (0 uni, 1 man, 3 de, ...)
  },
  atom uint8,
  arg_length uint8,
  arg bytes[arg_length],
  calc uncompressed uint8 = style == 0
}

packet FdoStream be {
  stream_id uint16,
  atoms FdoAtom[]
}
```

* The token is a `char[2]` **string**: you compare it with `"Dd"`, not with
  bytes.
* FDO atoms start with another bitfield: a 3-bit compression style and a
  5-bit value. Clients send the uncompressed style 0, which this
  description models exactly. Servers also use compressed styles where the
  layout depends on the style. That needs a conditional (union) field,
  which the language doesn't have yet. `uncompressed` tells you when to
  stop.

The `Dd` login stream is a sequence of `uni`, `man` (context) and `de`
(data entry) atoms. The screen name and password are the arguments of the
two `de_data` atoms (protocol 3, atom 1).

## 4. Decoding a session (Python)

```
$ cargo run -- generate examples/p3.packet -l python -p packets -o examples/out
$ PYTHONPATH=examples/out python3 examples/p3_demo.py
INIT from a Windows client, version 157.17, session flags 0x14d1
DATA token 'Dd', 83 byte(s) of FDO atoms
login: screen name 'someguy', password *********
ACK reply: 5afa0d00031010a40d
```

The core of the demo:

```python
for packet in packets(STREAM):               # framing + CRC check (section 2)
    if packet.type == INIT:
        init = P3Init.decode(packet.data)
        print(init.platform, init.client_major, init.client_minor)
    elif packet.type == DATA:
        message = P3Message.decode(packet.data)
        if message.token == "Dd":
            fields = [a.arg.decode() for a in FdoStream.decode(message.atoms).atoms
                      if a.uncompressed and (a.protocol, a.atom) == (3, 1)]
```

## 5. The same in Rust

([full program](../examples/p3_demo.rs))

```rust
let mut reader = PbReader::new(&bytes);
while reader.remaining_bits() > 0 {
    let start = reader.position_bits() / 8;
    let packet = P3Packet::decode_from(&mut reader)?;
    let raw = &bytes[start..reader.position_bits() / 8];
    let crc_ok = crc16_arc(&raw[3..raw.len() - 1]) == packet.crc;
    if packet.r#type == 0x20 {
        let message = P3Message::decode(&packet.data)?;
        let stream = FdoStream::decode(&message.atoms)?;
        println!("{}: {} atoms, crc ok {}", message.token, stream.atoms.len(), crc_ok);
    }
}
```

`type` is a Rust keyword, so the member is `r#type`. It is `type_` in C,
`Type` in Go and C#, and `@"type"` in Zig.

## 6. What's covered, and what isn't

| part | packet | tested with |
|------|--------|-------------|
| framing, all packet types | `P3Packet` | captured INIT, ACK, NAK, HEARTBEAT, DATA, malformed frames |
| DATA packets | `P3DataPacket`, `P3Message` | `Dd` login, `SD` |
| INIT | `P3InitPacket`, `P3Init` | captured INIT |
| FDO atoms | `FdoStream`, `FdoAtom` | login stream; a compressed atom is flagged |

Not covered: the CRC is checked by the application rather than by the
generated parser, compressed FDO atoms aren't decoded, and the 49-byte INIT
variant some clients send is left out. The first two would need new
language features (checksums, tagged unions).
